# 特征建模历史和依赖

这篇文档主要回答四个问题：

- 特征建模里的“历史树”和“依赖图”分别是什么意思
- `dune3d` 现在是怎么做历史和依赖的
- FreeCAD 的 DAG 依赖图相比之下解决了什么问题
- 用一个最简单例子说明线性历史和 DAG 的工作模式差别

先说结论：

- 历史树回答的是：先做了什么，后做了什么
- 依赖图回答的是：谁依赖谁，改一个对象会影响谁
- `dune3d` 现在是“线性特征历史为主，依赖关系为辅”
- FreeCAD 更接近“对象 DAG 为主，树状展示为辅”


## 1. 什么是历史树

历史树本质上是建模步骤序列。

例如：

```text
Sketch 1
-> Extrude 1
-> Fillet 1
-> Pattern 1
```

它表达的是：

- 先有草图
- 再拉伸
- 再圆角
- 再阵列

也就是“建模顺序”。

很多 CAD 界面里左侧看到的特征列表，本质上就是这种历史顺序的展示。


## 2. 什么是依赖图

依赖图表达的是对象之间的引用关系。

例如：

```text
Sketch -> Pad
Pad -> Fillet
Pad -> DatumPlane
DatumPlane -> Sketch002
Sketch002 -> Pocket
```

这里强调的不是“谁排在前面”，而是：

- `Fillet` 依赖 `Pad`
- `DatumPlane` 也依赖 `Pad`
- `Sketch002` 依赖 `DatumPlane`
- `Pocket` 依赖 `Sketch002`

所以依赖图回答的是：

- 谁是真正的上游
- 谁是真正的下游
- 改一个对象，哪些对象需要重算


## 3. `dune3d` 的历史主线：Group 顺序

`dune3d` 的建模历史主线很明确，就是 `Group` 序列。

`src/document/document.hpp`

```cpp
std::map<UUID, std::unique_ptr<Group>> m_groups;
std::vector<Group *> m_groups_sorted;
std::vector<const Group *> m_groups_sorted_const;
```

`Group` 自己有顺序索引：

`src/document/group/group.hpp`

```cpp
auto get_index() const
{
    return m_index;
}
void set_index(Badge<Document>, int index)
{
    m_index = index;
}
```

文档里会按这个顺序排序：

`src/document/document.cpp`

```cpp
void Document::update_groups_sorted()
{
    m_groups_sorted.clear();
    for (auto &[uu, it] : m_groups) {
        m_groups_sorted.push_back(it.get());
    }
    std::ranges::sort(m_groups_sorted, {}, [](auto a) { return a->get_index(); });
    ...
}
```

所以在 `dune3d` 里：

- 历史树 = `Group` 的线性顺序
- 这条顺序也是重建主链


## 4. `dune3d` 的依赖关系：引用信息

`dune3d` 也有依赖关系，但没有把它做成一个独立通用 DAG 调度核心。

依赖信息主要体现在 `Group` 的这些接口：

`src/document/group/group.hpp`

```cpp
virtual std::set<UUID> get_referenced_entities(const Document &doc) const;
virtual std::set<UUID> get_referenced_groups(const Document &doc) const;

virtual std::set<UUID> get_required_entities(const Document &doc) const;
virtual std::set<UUID> get_required_groups(const Document &doc) const;
```

默认实现会扫描“本组 entity/constraint 引用了谁”：

`src/document/group/group.cpp`

```cpp
std::set<UUID> Group::get_referenced_entities(const Document &doc) const
{
    std::set<UUID> r;
    if (m_active_wrkpl)
        r.insert(m_active_wrkpl);
    for (const auto &[uu, en] : doc.m_entities) {
        if (en->m_group == m_uuid) {
            auto refs = en->get_referenced_entities();
            r.insert(refs.begin(), refs.end());
        }
    }
    for (const auto &[uu, co] : doc.m_constraints) {
        if (co->m_group == m_uuid) {
            auto refs = co->get_referenced_entities();
            r.insert(refs.begin(), refs.end());
        }
    }
    return r;
}
```

再从 entity 反推出依赖了哪些 group：

```cpp
std::set<UUID> Group::get_referenced_groups(const Document &doc) const
{
    auto ents = get_referenced_entities(doc);
    std::set<UUID> r;
    for (auto &en_uu : ents) {
        auto &en = doc.get_entity(en_uu);
        r.insert(en.m_group);
    }
    return r;
}
```

所以 `dune3d` 的依赖关系是有的，但整体风格是：

- 历史链是主结构
- 依赖关系是辅助信息


## 5. `dune3d` 的重建机制

`dune3d` 改完一个对象后，不是跑一个完整 DAG 调度器，而是：

- 找到最早受影响的 group
- 从那里开始按历史顺序往后重建

脏标记字段：

`src/document/document.hpp`

```cpp
UUID m_first_group_generate;
UUID m_first_group_solve;
UUID m_first_group_update_solid_model;
```

标记传播：

`src/document/document.cpp`

```cpp
void Document::set_group_generate_pending(const UUID &group)
{
    update_group_if_less(m_first_group_generate, group);
    set_group_solve_pending(group);
}

void Document::set_group_solve_pending(const UUID &group)
{
    update_group_if_less(m_first_group_solve, group);
    set_group_update_solid_model_pending(group);
}
```

真正重建：

```cpp
void Document::update_pending(const UUID &last_group_to_update_i, const std::vector<EntityAndPoint> &dragged)
{
    ...
    if (index >= first_generate_index) {
        generate_group(*group);
    }
    ...
    if (index >= first_solve_index) {
        solve_group(*group, dragged);
    }
    if (index >= first_update_solid_model_index) {
        update_solid_model(*group);
    }
}
```

所以 `dune3d` 的工作模式可以概括成：

- 用引用关系判断“从哪一组开始可能坏了”
- 用线性 group 顺序负责真正的重建推进


## 6. `dune3d` 里依赖关系的实际用途

依赖关系不是摆设，当前至少有几个明确用途。

### 6.1 检查 group 重排是否合法

`src/document/document.cpp`

```cpp
for (auto gr : groups_new_order) {
    available_groups.insert(gr->m_uuid);
    auto referenced_groups = gr->get_referenced_groups(*this);
    if (!std::ranges::includes(available_groups, referenced_groups))
        return false;
}
```

意思是：

- 如果你把一个 group 拖到它依赖对象前面
- 那这个顺序就非法

这就是：

- 历史顺序决定排列
- 依赖关系约束这个排列不能乱

### 6.2 删除对象时做依赖传播

文档删除逻辑里也会根据依赖关系继续找“还得跟着删什么”。

`src/document/document.cpp`

```cpp
auto reqs = it->get_required_entities(*this);
...
auto reqs = it->get_required_groups(*this);
```

也就是说：

- 依赖关系还参与删除影响范围的推导


## 7. `dune3d` 的 undo/redo 和历史树不是一回事

这个很容易混。

`dune3d` 的 undo/redo 用的是文档快照栈，而不是特征历史树本身。

`src/util/history_manager.hpp`

```cpp
class HistoryManager : public Changeable {
public:
    class HistoryItem {
    public:
        HistoryItem(const std::string &c) : comment(c) {}
        const std::string comment;
    };
    ...
};
```

文档快照项：

`src/core/core.cpp`

```cpp
class HistoryItemDocument : public HistoryManager::HistoryItem {
public:
    HistoryItemDocument(const Document &doc, const std::string &cm) : HistoryManager::HistoryItem(cm), document(doc)
    {
    }
    Document document;
};
```

push 时压进去的是整个 `Document`：

```cpp
void Core::DocumentInfo::history_push(const std::string &comment)
{
    m_history_manager.push(std::make_unique<HistoryItemDocument>(m_doc.value(), comment));
}
```

所以要区分两个“历史”：

- 特征历史：`Group` 顺序
- 撤销重做历史：`Document` 快照序列


## 8. FreeCAD 的 DAG 式依赖

FreeCAD 这块更偏“对象图”。

根据 FreeCAD 源码文档：

- `App::Document` 明确提到使用 adjacency list 处理对象依赖，用于 recompute
- `App::DocumentObject` 提供：
  - `getInList()`
  - `getOutList()`
  - `getInListRecursive()`
  - `getOutListRecursive()`

这表示 FreeCAD 的对象依赖不是单纯按列表顺序理解，而是图结构。

参考：

- `App::Document`: https://freecad.github.io/SourceDoc/d8/d3e/classApp_1_1Document.html
- `App::DocumentObject`: https://freecad.github.io/SourceDoc/d2/de4/classApp_1_1DocumentObject.html

在 FreeCAD 里可以这么理解：

- 模型树/对象树：主要给用户看
- `InList/OutList`：主要给系统算依赖和 recompute

也就是说：

- 树是展示层
- DAG 是真实依赖层


## 9. FreeCAD 的 DAG 相比 `dune3d` 解决了什么问题

这里说的是功能表达能力，不是性能。

### 9.1 更自然地表达分支

线性历史擅长表达：

```text
A -> B -> C -> D
```

但真实模型常常是：

```text
A -> B -> C
 \-> D -> E
```

在 DAG 里这很自然。

在线性历史里，只能硬压成一条主链，分支语义会被弱化。

### 9.2 更自然地表达共享上游

例如一个 `Spreadsheet` 同时驱动：

- 底板草图
- 孔位置草图
- 基准面偏移

这种“一个源头驱动多个下游”是 DAG 的强项。

线性历史虽然也能引用这个参数源，但主结构仍然是一条顺序链，无法天然表达“共享节点”。

### 9.3 更自然地表达多输入对象

例如：

- `Pocket` 依赖实体 + 草图
- `Boolean` 依赖 argument + tool

在 DAG 里直接是：

```text
BodyA -> Boolean
BodyB -> Boolean
```

而在线性历史里，很容易被压成：

```text
BodyA -> BodyB -> Boolean
```

这样顺序有了，但“Boolean 同时依赖 A 和 B”这个语义不够自然。

### 9.4 更容易区分“顺序”和“依赖”

线性历史容易让人把：

- 排在前面
- 真正依赖

这两件事混起来。

DAG 则能明确区分：

- 这只是显示顺序
- 那才是逻辑依赖


## 10. `dune3d` 线性历史的优缺点

### 优点

- 模型主线很清楚
- 对典型单主链特征建模非常自然
- 文件和重建逻辑更简单
- 系统心智模型容易理解：从前往后做

### 局限

- 不擅长表达复杂分支
- 不擅长表达共享上游节点
- 不擅长表达真正的多输入依赖网络
- 更容易把“时间顺序”和“逻辑依赖”混在一起

所以它适合：

- `Sketch -> Extrude -> Fillet -> Pattern` 这种单主链特征建模

不太适合：

- 大量跨对象复用
- 多 body 深度依赖
- 公共参数源驱动多个分支
- 更复杂的对象网络式建模


## 11. 一个最简单的例子：底板 + 两孔 + 耳朵

这个例子足够小，但已经能说明线性历史和 DAG 的区别。

### 出现的特征含义

- `Spreadsheet`：参数表，统一存尺寸
- `Sketch_Base`：底板轮廓草图
- `Pad`：把草图拉伸成实体
- `HoleSketch`：孔位置/孔轮廓草图
- `Pocket`：拉伸切除，用来打孔
- `DatumPlane`：基准面，给后续草图提供参考
- `Sketch_Ear`：耳朵草图
- `Pad_Ear`：把耳朵草图拉伸成实体

### 真实依赖关系（DAG 视角）

```text
Spreadsheet -> Sketch_Base -> Pad
Spreadsheet -> HoleSketch -> Pocket
Spreadsheet -> DatumPlane -> Sketch_Ear -> Pad_Ear

Pad -> Pocket
Pad -> DatumPlane
```

画成更直观的图：

```text
                -> HoleSketch -> Pocket
               /                 ^
Spreadsheet ->                    |
               \-> Sketch_Base -> Pad
                \
                 -> DatumPlane -> Sketch_Ear -> Pad_Ear
                         ^
                         |
                        Pad
```

这个图里有三个关键点：

- `Spreadsheet` 是共享上游
- `Pad` 是分叉节点
- `Pocket` 是多输入对象

### 线性历史视角

如果硬压成线性历史，只能变成：

```text
Spreadsheet
-> Sketch_Base
-> Pad
-> HoleSketch
-> Pocket
-> DatumPlane
-> Sketch_Ear
-> Pad_Ear
```

它能执行，但表达不准：

- 看不出 `Spreadsheet` 同时驱动多个对象
- 看不出 `Pad` 后面分出了两条支路
- 看不出 `Pocket` 同时依赖 `Pad` 和 `HoleSketch`

这就是线性和 DAG 的本质区别：

- 线性历史更像“建模脚本顺序”
- DAG 更像“真实对象依赖网络”


## 12. 总结

这套概念可以压缩成下面几句：

- 历史树解决“先做什么、后做什么”
- 依赖图解决“谁依赖谁、谁影响谁”
- `dune3d` 当前是线性 `Group` 历史主导，依赖关系作为辅助信息
- FreeCAD 更偏对象 DAG 主导，模型树更多是展示和组织层

所以两者不是简单的“谁高级谁低级”，而是偏重点不同：

- `dune3d` 更适合单主链特征建模
- FreeCAD 的 DAG 更适合复杂对象网络、共享参数源、分支依赖和多输入对象

如果只记一句：

- `dune3d` 更像“从前往后的一条建模链”
- FreeCAD 更像“由对象依赖关系组成的一张图”
