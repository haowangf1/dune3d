# 工程文件结构

这篇主要回答三个问题：

- `dune3d` 的工程文件里到底保存了什么
- 打开文件时，程序如何从这些内容重建模型
- 这种做法和 FreeCAD 的主要区别是什么

先说结论：

- `dune3d` 的 `.d3ddoc` 本质上是参数化文档文件
- 它主要保存 `groups`、`entities`、`constraints`、`version`
- 不直接保存 OCC 的 `TopoDS_Shape` / B-rep 实体结果
- 打开文件后，会重新跑一遍文档重建流程，把实体和渲染数据重新算出来


## 1. 主工程文件保存什么

主工程文件保存入口在 `Core::DocumentInfo::save()`。

`src/core/core.cpp`

```cpp
void Core::DocumentInfo::save()
{
    if (is_read_only())
        return;
    if (has_path()) {
        m_doc->m_version.update_file_from_app();
        save_json_to_file(m_path, m_doc->serialize());
        pictures_save(*m_doc, get_picture_dir_from_document_filename(m_path));
        m_needs_save = false;
    }
}
```

这里能看出两点：

- 主文档内容来自 `m_doc->serialize()`
- 图片资源会单独保存到旁边目录

真正写文件的是 `save_json_to_file(...)`：

`src/util/util.cpp`

```cpp
void save_json_to_file(const std::filesystem::path &filename, const json &j)
{
    Glib::file_set_contents(filename.string(), j.dump(4));
}
```

所以 `.d3ddoc` 就是一个 JSON 文档文件。


## 2. Document 序列化了哪些核心内容

`src/document/document.cpp`

```cpp
json Document::serialize() const
{
    auto j = json{{"type", "document"}};
    m_version.serialize(j);
    {
        auto o = json::object();
        for (const auto &[uu, it] : m_groups) {
            o[uu] = it->serialize(*this);
        }
        j["groups"] = o;
    }
    {
        auto o = json::object();
        for (const auto &[uu, it] : m_entities) {
            if (it->m_kind == ItemKind::USER)
                o[uu] = it->serialize();
        }
        j["entities"] = o;
    }
    {
        auto o = json::object();
        for (const auto &[uu, it] : m_constraints) {
            o[uu] = it->serialize();
        }
        j["constraints"] = o;
    }
    return j;
}
```

所以主文件里主要有：

- `version`
- `groups`
- `entities`
- `constraints`

这里还有一个很关键的细节：

```cpp
if (it->m_kind == ItemKind::USER)
    o[uu] = it->serialize();
```

这表示：

- 只保存用户创建的 entity
- 运行时派生出来的 `GENRERATED` entity 不直接写进工程文件

比如：

- extrude/revolve 自动生成的 3D 辅助线
- 某些 group 运行时复制出来的显示实体

这些都属于“可重建的派生数据”，不是工程文件主数据。


## 3. 工程文件不保存什么

从 `Document::serialize()` 就能直接看出来，主文件里没有这些东西：

- `TopoDS_Shape`
- `SolidModelOcc::m_shape`
- `SolidModelOcc::m_shape_acc`
- 三角化后的 `face::Faces`
- 渲染状态
- 当前工具状态
- 当前选中状态

而 OCC shape 真正存放的位置在运行时对象里：

`src/document/solid_model/solid_model_occ.hpp`

```cpp
class SolidModelOcc : public SolidModel {
public:
    TopoDS_Shape m_shape;
    TopoDS_Shape m_shape_acc;
    Color m_color;
    ...
};
```

这说明：

- OCC 的 B-rep 结果只存在运行时内存里
- 不直接序列化进 `.d3ddoc`

所以答案很明确：

- `dune3d` 工程文件里没有 B-rep 持久化表达


## 4. 一个简化的 `.d3ddoc` 结构示意

实际文件会更长，但大体结构就是这样：

```json
{
  "type": "document",
  "app_version": 37,
  "file_version": 37,
  "groups": {
    "group-uuid-1": {
      "type": "reference",
      "index": 0,
      "name": "Reference",
      "body": {
        "name": "Body"
      }
    },
    "group-uuid-2": {
      "type": "sketch",
      "index": 1,
      "name": "Sketch 1",
      "active_wrkpl": "wrkpl-uuid"
    },
    "group-uuid-3": {
      "type": "extrude",
      "index": 2,
      "name": "Extrude 1",
      "source_group": "group-uuid-2",
      "wrkpl": "wrkpl-uuid",
      "dvec": [0, 0, 10]
    }
  },
  "entities": {
    "entity-uuid-1": {
      "type": "line2d",
      "group": "group-uuid-2",
      "...": "..."
    }
  },
  "constraints": {
    "constraint-uuid-1": {
      "type": "horizontal",
      "group": "group-uuid-2",
      "...": "..."
    }
  }
}
```

这个示意最重要的是传达结构：

- group 记录建模步骤
- entity 记录几何输入
- constraint 记录几何关系
- 文件不直接存 extrude 之后的实体 B-rep


## 5. 文件如何被读取

文件加载入口：

`src/document/document.cpp`

```cpp
Document Document::new_from_file(const std::filesystem::path &path)
{
    return Document{load_json_from_file(path), path.parent_path()};
}
```

真正构造时按三大类分别读取：

```cpp
Document::Document(const json &j, const std::filesystem::path &containing_dir) : m_version(app_version, j)
{
    for (const auto &[uu, it] : j.at("entities").items()) {
        load_and_log(m_entities, "Entity", uu, it, containing_dir);
    }
    for (const auto &[uu, it] : j.at("constraints").items()) {
        load_and_log(m_constraints, "Constraint", uu, it);
    }
    for (const auto &[uu, it] : j.at("groups").items()) {
        load_and_log(m_groups, "Group", uu, it);
    }
    update_groups_sorted();
    ...
}
```

也就是：

- 先把参数化文档结构读进内存
- 这时只有文档数据，不保证实体结果已经存在


## 6. 读取后如何重建模型

重点在这里。加载完不是直接“拿到现成实体”，而是立刻触发重建。

还是 `src/document/document.cpp`：

```cpp
if (m_groups.size())
    set_group_generate_pending(get_groups_sorted().front()->m_uuid);
update_pending();
erase_invalid();
```

也就是说：

- 从第一组开始标记为 pending
- 调 `update_pending()`
- 重新生成派生 entity、求解约束、重建实体

`update_pending()` 的主流程：

```cpp
if (index >= first_generate_index) {
    generate_group(*group);
}
...
if (index >= first_solve_index) {
    solve_group(*group, dragged);
}
if (index >= first_update_solid_model_index) {
    update_solid_model(*group);
}
```

所以文件打开后的核心动作是：

1. 读 JSON
2. 还原 `groups / entities / constraints`
3. 按 group 顺序重新：
   - `generate`
   - `solve`
   - `update_solid_model`


## 7. 为什么只靠这些参数就能复现模型

因为 `dune3d` 的设计本来就是参数化重建模式。

模型结果不是作为“最终实体快照”存文件，而是作为“可重建结果”存在。

也就是说，只要这些输入完整：

- group 参数
- entity 几何参数
- constraint 约束关系
- 必要外部资源

就可以重新算出模型。

但这里要注意两点：

- 这是“参数重建复现”，不是“原始 B-rep 二进制逐字回放”
- 如果外部 STEP / 图片资源缺失，或者算法/内核版本发生变化，结果可能出现差异


## 8. 这意味着什么：建模步骤必须落到 Group

因为打开文件时，重建主线是按 `Group` 顺序推进的，所以：

- 任何会影响后续模型结果的建模动作
- 都必须在文档里有对应的 group 表达

例如：

- sketch
- extrude
- revolve
- loft
- fillet
- array

都需要作为 group 存在。

否则打开文件后，程序就不知道该按什么步骤重建模型。

所以可以把 `dune3d` 理解成：

- 模型历史几乎就是一串 `Group`


## 9. 从工程文件到实体结果的最小链路

以一个草图拉伸为例：

### 9.1 工程文件里保存的是 sketch + extrude 参数

不是保存最终 box 的 B-rep。

### 9.2 读文件后，extrude group 进入实体重建

`src/document/group/group_extrude.cpp`

```cpp
void GroupExtrude::update_solid_model(const Document &doc)
{
    m_solid_model = SolidModel::create(doc, *this);
}
```

### 9.3 从 document 中提取 source group 的草图轮廓

`src/document/solid_model/solid_model_extrude.cpp`

```cpp
auto face_builder = FaceBuilder::from_document(doc, group.m_wrkpl, group.m_source_group, offset);
```

### 9.4 OCC 生成 shape

```cpp
mod->m_shape = BRepPrimAPI_MakePrism(face_builder.get_faces(), gp_Vec(dvec.x, dvec.y, dvec.z));
```

### 9.5 与前序实体累计

`src/document/solid_model/solid_model_occ.cpp`

```cpp
const auto last_solid_model = dynamic_cast<const SolidModelOcc *>(get_last_solid_model(doc, group));
update_acc(operation, last_solid_model);
```

### 9.6 再三角化进入渲染

```cpp
triangulate();
find_edges();
```

所以这条链是：

```text
.d3ddoc(JSON)
  -> Document(groups/entities/constraints)
  -> update_pending()
  -> Group::update_solid_model()
  -> OCC TopoDS_Shape
  -> triangulate
  -> render
```

## 11. 和 FreeCAD 的主要区别

这里说最核心的结构区别，不展开到 FreeCAD 全部对象系统。

### dune3d

- 主工程文件偏“纯参数化文档”
- 保存：
  - group
  - entity
  - constraint
  - version
- 不直接保存运行时 OCC `TopoDS_Shape`
- 打开文件后，从头按 group 重建实体结果

### FreeCAD

- `FCStd` 是更重的文档容器，不是这种单一 JSON 文档
- 文档里不只是极简参数树
- 其对象/shape 持久化方式比 `dune3d` 更重、更复杂
- 用户可以直接创建 box 这类 primitive，但它仍然通常是文档树里的参数化对象，不是脱离对象系统的“裸 shape”

所以两者的主要差别不是“有没有参数化对象”，而是：

- `dune3d` 更偏“只存输入，打开后重建输出”
- FreeCAD 更偏“文档容器更重，对对象和形状结果的承载更完整”


## 12. 这种设计的优缺点

### 优点

- 文件格式简单
- 文档语义清晰，就是“可重建输入”
- 不需要处理 shape 缓存与参数失配问题
- 版本升级和兼容逻辑相对更干净

### 代价

- 打开文件时要重新重建
- 大模型、重布尔、复杂 loft/array/fillet 可能更慢
- 运行时开销更依赖 OCC 重建和三角化

也就是说，`dune3d` 当前更像：

- 存参数
- 不存最终实体缓存
- 用重建换简洁


## 13. 总结

`dune3d` 的工程文件结构，可以用一句话概括：

- `.d3ddoc` 保存的是参数化建模文档，不是实体结果快照

具体表现为：

- 文件里主要有 `groups / entities / constraints / version`
- 不直接保存 OCC `TopoDS_Shape`
- 打开后通过 `update_pending()` 按 group 顺序重新生成、求解、建模
- 任何影响模型结果的建模动作，都必须能落成一个 group，才能被持久化和重建

所以它和 FreeCAD 的核心区别是：

- `dune3d` 更轻、更纯参数化
- FreeCAD 的文档容器和对象/形状持久化更重

这也是为什么 `dune3d` 的工程文件简单，但复杂模型打开时更依赖重建性能。
