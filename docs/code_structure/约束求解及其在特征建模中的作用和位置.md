# 约束求解及其在特征建模中的作用和位置

这篇只回答 3 个问题：

- 约束求解在这个库里具体做什么
- 它在特征建模主流程里处于什么位置
- SolveSpace、`src/document/constraint`、`src/system/system.cpp` 三层分别负责什么

先给结论：

- 约束求解负责把当前 group 里的草图和参数化几何更新到一致状态
- 特征建模随后使用这个状态去生成 solid model
- 在总流程里，它位于 `generate -> solve -> update_solid_model` 中间


## 1. 它在总流程里的位置

特征建模的主流程里，重建入口是：

- `Core::rebuild(...)`

核心会进入：

```cpp
get_current_document().update_pending();
```

而 `Document::update_pending(...)` 的关键三阶段是：

```cpp
if (index >= first_generate_index) {
    generate_group(*group);
}
if (index >= first_solve_index) {
    solve_group(*group, dragged);
}
if (index >= first_update_solid_model_index) {
    update_solid_model(*group);
}
```

所以总流程可以直接记成：

```text
generate
  -> solve
  -> update_solid_model
```

这里的 `solve`，就是约束求解所在的位置。

它前面是：

- group 的派生几何生成

它后面是：

- solid model 更新


## 2. 约束求解具体在更新什么

约束求解更新的是当前 group 里的参数化几何状态。常见对象包括：

- 2D 点、线、圆、圆弧、Bezier
- 它们之间的重合、水平、垂直、距离、角度、中点等约束
- group 当前的自由度和求解状态

对后续特征建模来说，关键点是：

- 特征并不直接吃“用户操作意图”
- 它吃的是当前 `Document` 里已经更新过的几何状态

例如 `Extrude` 在生成实体时，会从 `source group` 里取输入轮廓，再交给 `FaceBuilder` 和 OCC：

```cpp
auto face_builder = FaceBuilder::from_document(doc, group.m_wrkpl, group.m_source_group, offset);
mod->m_shape = BRepPrimAPI_MakePrism(face_builder.get_faces(), gp_Vec(dvec.x, dvec.y, dvec.z));
```

所以这里的依赖顺序是：

```text
先更新草图 / 参数状态
  -> 再整理输入 face
  -> 再生成实体
```


## 3. `solve_group(...)` 真正做了什么

位置：

- `src/document/document.cpp`

关键代码：

```cpp
void Document::solve_group(Group &group, const std::vector<EntityAndPoint> &dragged)
{
    ...
    System system{*this, group.m_uuid};
    for (const auto &[en, pt] : dragged) {
        system.add_dragged(en, pt);
    }
    const auto res = system.solve();
    group.m_solve_result = res.result;
    group.m_dof = res.dof;
    ...
    system.update_document();
}
```

这段做了 4 件事：

- 构造当前 group 的约束系统 `System`
- 运行 `system.solve()`
- 记录求解结果：
  - `group.m_solve_result`
  - `group.m_dof`
- 用 `system.update_document()` 把求解后的参数写回文档

所以 `solve_group(...)` 的职责可以概括成：

- 为当前 group 组装求解系统
- 求解约束
- 把结果回写到 `Document`


## 4. 为什么特征建模阶段离不开这一步

因为很多特征的输入都来自上游 group 的草图或参数化对象。

在 `Extrude` 这种典型流程里：

- `m_source_group` 指向输入 group
- `FaceBuilder::from_document(...)` 从这个 group 中提取轮廓
- 再由 OCC 生成实体

也就是说，特征建模之前，需要先保证：

- 输入草图对象的位置、尺寸、关系都已经更新到当前正确状态

因此在 `update_pending()` 里，`solve` 放在 `update_solid_model` 之前是合理且必要的。


## 5. 这个库的求解器到底是谁提供的

这里要分三层看。

### 5.1 底层求解内核：SolveSpace

这个项目直接把 SolveSpace 编进来了。

`meson.build` 里有：

```meson
subdir('3rd_party/solvespace')
```

`src/system/system.cpp` 里直接引用了 SolveSpace 头文件：

```cpp
#include "solvespace/src/solvespace.h"
#include "solvespace/src/sketch.h"
```

并且 `System` 内部持有：

```cpp
std::unique_ptr<SolveSpace::System> m_sys;
```

所以底层数值求解引擎是 SolveSpace。

### 5.2 dune3d 自己负责的部分

dune3d 自己负责的是：

- `Document / Group / Entity / Constraint` 这套文档模型
- `src/document/constraint/*` 里的约束对象定义
- `src/system/system.cpp` 里对 SolveSpace 的桥接
- 求解结果回写文档
- 和 tool / rebuild / UI / history 的整合

所以准确说法是：

- 底层求解用 SolveSpace
- 上层文档模型、约束对象、桥接和工作流集成由 dune3d 自己做


## 6. `src/document/constraint` 这一层是干嘛的

这一层主要是在定义“文档里有哪些约束对象”。

它负责：

- 每种约束保存哪些字段
- 它引用哪些实体 / 点 / workplane
- 怎么序列化 / 反序列化
- 怎么被文档系统和 UI 识别

所以这层更准确的定位是：

- dune3d 的约束定义层 / 文档模型层

不是 SolveSpace 原始求解器源码本体。


## 7. 约束和实体是怎么进入 SolveSpace 的

桥接发生在：

- `src/system/system.cpp`

`System` 构造时会遍历当前 group 里的实体和约束：

```cpp
for (auto entity : entities) {
    entity->accept(*this);
}
for (auto constraint : constraints) {
    constraint->accept(*this);
}
```

意思是：

- dune3d 自己的 `Entity`
- dune3d 自己的 `Constraint`

都会通过 visitor 方式交给 `System`。

然后 `System` 再把它们翻译成 SolveSpace 的内部对象。

例如 `ConstraintHV` 的桥接代码：

```cpp
void System::visit(const ConstraintHV &constraint)
{
    ...
    ConstraintBase cb = {};
    if (constraint.get_type() == Constraint::Type::HORIZONTAL)
        cb.type = ConstraintBase::Type::HORIZONTAL;
    else
        cb.type = ConstraintBase::Type::VERTICAL;
    cb.workplane.v = get_entity_ref(EntityRef{constraint.m_wrkpl, 0});
    cb.ptA.v = m_entity_refs_r.at(constraint.m_entity1);
    cb.ptB.v = m_entity_refs_r.at(constraint.m_entity2);

    SK.constraint.Add(&cb);
}
```

这段体现了三层结构：

- 文档层：`ConstraintHV`
- 桥接层：`System::visit(...)`
- 求解内核层：`SK.constraint.Add(&cb)` 进入 SolveSpace

实体也会做同样的翻译。比如 `EntityLine2D` 会被转换成 SolveSpace 的点和线段：

```cpp
void System::visit(const EntityLine2D &line)
{
    ...
    eb.type = EntityBase::Type::POINT_IN_2D;
    ...
    SK.entity.Add(&eb);
    ...
    eb.type = EntityBase::Type::LINE_SEGMENT;
    ...
    SK.entity.Add(&eb);
}
```

所以求解系统的构造不是只喂约束，而是：

- 先喂实体
- 再喂约束


## 8. 求解完成后，结果怎么影响后续建模

`solve_group(...)` 的最后一步是：

```cpp
system.update_document();
```

也就是把求解后的参数回写到文档。

因此后续 `update_solid_model(...)` 看到的输入，已经是求解后的当前状态。

这就是它在主流程中的作用：

- 它不是一个孤立分析步骤
- 它直接决定后续特征建模拿到的输入几何


## 9. 一个具体例子：约束求解在参数建模里到底起什么作用

可以用“草图轮廓 -> 特征输入”这个最典型的场景理解。

假设当前 group 里有一组 2D 草图实体：

- 若干 `EntityLine2D`
- 若干 `EntityPoint2D`
- 一些约束：
  - 点重合
  - 水平/垂直
  - 距离
  - 中点

这些对象先存活在 `Document` 里，约束对象本身也只是文档数据。  
例如水平/垂直约束在文档层保存的是：

```cpp
class ConstraintHV : public Constraint, public IConstraintWorkplane {
public:
    EntityAndPoint m_entity1;
    EntityAndPoint m_entity2;
    UUID m_wrkpl;
};
```

也就是说，这一层只是在描述：

- 哪两个点受约束
- 约束发生在哪个工作平面里

当 `solve_group(...)` 运行时，会构造一个 `System`：

```cpp
System system{*this, group.m_uuid};
const auto res = system.solve();
system.update_document();
```

在 `System` 构造阶段，当前 group 里的实体和约束会被遍历并翻译给 SolveSpace：

```cpp
for (auto entity : entities) {
    entity->accept(*this);
}
for (auto constraint : constraints) {
    constraint->accept(*this);
}
```

例如一条 2D 线会被翻译成 SolveSpace 的点和线段：

```cpp
void System::visit(const EntityLine2D &line)
{
    ...
    eb.type = EntityBase::Type::POINT_IN_2D;
    ...
    SK.entity.Add(&eb);
    ...
    eb.type = EntityBase::Type::LINE_SEGMENT;
    ...
    SK.entity.Add(&eb);
}
```

而水平/垂直约束会被翻译成 SolveSpace 的约束对象：

```cpp
void System::visit(const ConstraintHV &constraint)
{
    ...
    if (constraint.get_type() == Constraint::Type::HORIZONTAL)
        cb.type = ConstraintBase::Type::HORIZONTAL;
    else
        cb.type = ConstraintBase::Type::VERTICAL;
    cb.workplane.v = get_entity_ref(EntityRef{constraint.m_wrkpl, 0});
    cb.ptA.v = m_entity_refs_r.at(constraint.m_entity1);
    cb.ptB.v = m_entity_refs_r.at(constraint.m_entity2);

    SK.constraint.Add(&cb);
}
```

然后 `system.solve()` 会根据这些实体和约束一起求解，  
把当前 group 的几何参数更新到一个满足约束的状态；  
再通过 `system.update_document()` 把结果写回 `Document`。

这一步在参数建模里的实际作用是：

- 保证草图轮廓是当前一致状态
- 保证点位、边方向、尺寸关系都已经更新
- 让后续特征拿到的是“解算后的几何输入”

所以后面的特征建模代码，比如：

```cpp
auto face_builder = FaceBuilder::from_document(doc, group.m_wrkpl, group.m_source_group, offset);
mod->m_shape = BRepPrimAPI_MakePrism(face_builder.get_faces(), gp_Vec(dvec.x, dvec.y, dvec.z));
```

它依赖的其实就是这个“已经解算完成的草图状态”。

把这个例子压缩成一句话：

```text
约束求解把参数化草图更新到当前正确状态，
特征建模再用这个状态作为输入生成实体。
```


## 10. 它在“数据更新 -> 重绘”总链里的位置

把整条主链缩成一条：

```text
用户编辑 / 新建特征
  -> Core::rebuild()
  -> Document::update_pending()
       -> generate
       -> solve
       -> update_solid_model
  -> Core::signal_rebuilt()
  -> Editor 刷新 UI / 画布
  -> Canvas::on_render()
```

所以约束求解的位置很明确：

- 在文档重建阶段
- 在 solid model 更新之前
- 在 UI 重绘之前


## 11. 要害总结

- 约束求解负责把当前 group 的草图和参数化几何更新到一致状态
- 在总流程里，它位于 `generate -> solve -> update_solid_model` 中间
- `solve_group(...)` 的职责是：构造当前 group 的 `System`，运行 `solve()`，记录 DOF/状态，并把结果回写到文档
- 底层求解内核使用的是 SolveSpace
- dune3d 自己实现的是文档层约束对象、实体/约束到 SolveSpace 的桥接，以及与 rebuild / UI / history 的整体集成
- `src/document/constraint` 是约束定义层，`src/system/system.cpp` 是桥接层，`3rd_party/solvespace` 是底层求解引擎
