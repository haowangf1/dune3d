# tool工具机制

## 1. 一条完整调用链长什么样

以鼠标移动事件为例，完整链路大致是：

- GTK 层收到鼠标移动事件
- `Editor::handle_cursor_move()` 被调用
- `Editor` 构造 `ToolArgs`，把事件类型设为 `ToolEventType::MOVE`
- `Editor` 调用 `m_core.tool_update(args)`
- `Core::tool_update()` 检查当前是否有活动中的 tool
- 如果 `m_tool != nullptr`，则调用当前 tool 的 `m_tool->update(args)`
- tool 根据这次事件更新自己的内部状态
- `Editor::tool_process(...)` 再把这些状态刷新到 UI 和 canvas 上

可以把这条链理解成：

- GTK 负责产生事件
- `Editor` 负责收事件并打包
- `Core` 负责把事件转发给当前活动 tool
- tool 自己决定这次事件意味着什么

## 2. 为什么后续会一直进 `update()`

不是 tool 自己在循环调用 `update()`，而是：

- 外部事件一直在发生，比如鼠标移动、点击、键盘动作
- 只要当前 tool 还活着，`Editor` 就会把这些事件继续转发给它
- `Core::tool_update()` 再把事件交给当前的 `m_tool->update(args)`

所以“持续进入 `update()`”的根本原因是：

- 当前存在活动中的 tool（`m_tool != nullptr`）
- 后续输入事件都会被事件分发系统路由给这个 tool

直到 tool 返回：

- `COMMIT`
- `REVERT`
- `END`

然后 `Core` 把当前 tool 结束掉，后续事件才不会再进这个 tool 的 `update()`。
