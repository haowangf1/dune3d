# 特征建模-数据更新-重绘主流程

这篇只抓主线：

- 用户新增一个特征时，`Document` 怎么改
- 改完后，数据怎么重新生成
- solid model 怎么更新
- 最后界面和画布怎么刷新

用 `GroupExtrude` 作为样本最合适，因为它同时覆盖了：

- group 创建
- source group 引用
- 派生几何生成
- solid model 生成
- 渲染刷新


## 1. 总体主链

可以先记这条线：

```text
用户新增特征
  -> Editor::on_add_group(...)
  -> doc.insert_group<...>()
  -> finish_add_group(...)
  -> doc.set_group_generate_pending(...)
  -> m_core.rebuild(...)
  -> Document::update_pending()
       -> generate
       -> solve
       -> update_solid_model
  -> Core::signal_rebuilt()
  -> Editor 刷新 UI / 画布
  -> Canvas::on_render()
```


## 2. 第一步：先把 group 写进 Document

入口在：

- `src/editor/editor_workspace_browser.cpp`
- `Editor::on_add_group(...)`

以 `Extrude` 为例：

```cpp
auto &group = doc.insert_group<GroupExtrude>(UUID::random(), current_group.m_uuid);
new_group = &group;
group.m_wrkpl = current_group.m_active_wrkpl;
group.m_dvec = doc.get_entity<EntityWorkplane>(group.m_wrkpl).get_normal_vector();
group.m_source_group = current_group.m_uuid;
```

这一步做的事很明确：

- 往 `Document` 里插入一个新的 `GroupExtrude`
- 绑定工作平面 `m_wrkpl`
- 设置默认拉伸方向 `m_dvec`
- 记录输入来源 `m_source_group`

也就是说，`on_add_group(...)` 的职责是：

- 先把“特征节点”和它的基本参数落到文档里


## 3. `WITH_BODY` 是什么

`on_add_group(...)` 末尾还有一段：

```cpp
if (new_group && add_group_mode == WorkspaceBrowserAddGroupMode::WITH_BODY)
    new_group->m_body.emplace();
```

这里的 `m_body` 不是 OCC shape，也不是实体几何本体。  
它只是 `Group` 上的一个 body 元数据入口。

定义在：

- `src/document/group/group.hpp`

```cpp
class Body {
public:
    std::string m_name = "Body";
    std::optional<Color> m_color;
};

std::optional<Body> m_body;
```

它的含义是：

- 让当前 group 成为一个新的 body 起点

后续 group 的 body 归属，是按 group 顺序往后继承的。  
这一点在 `Group::find_body(...)` 里能看出来：

```cpp
for (auto group : doc.get_groups_sorted()) {
    if (group->m_body)
        body_group = group;
    if (group == this)
        return {body_group->m_body.value(), *body_group};
}
```

所以 `WITH_BODY` 影响的是：

- 左侧 workspace browser 的 body 分组结构
- body 名称/颜色
- 渲染时按 body 聚合 solid model
- 导出时按 body 分组


## 4. 第二步：`finish_add_group(...)` 让新特征生效

代码在：

- `src/editor/editor_workspace_browser.cpp`

```cpp
void Editor::finish_add_group(Group *new_group)
{
    if (!new_group)
        return;
    CanvasUpdater canvas_updater{*this};
    auto &doc = m_core.get_current_document();
    auto group_type = new_group->get_type();
    new_group->m_name = doc.find_next_group_name(group_type);
    doc.set_group_generate_pending(new_group->m_uuid);
    m_core.set_needs_save();
    m_core.rebuild("add group");
    m_workspace_browser->update_documents(get_current_document_views());
    m_workspace_browser->select_group(new_group->m_uuid);
    ...
}
```

这一步做了 5 件事：

- 给新 group 起默认名字
- 标记这个 group 之后需要重新生成
- 标记文档需要保存
- 调 `m_core.rebuild(...)`
- 刷新左侧树，并选中新 group

如果这个 group 还缺交互输入，还会继续启动 tool，比如：

```cpp
else if (group_type == Group::Type::REVOLVE) {
    trigger_action(ToolID::SELECT_REVOLVE_AXIS);
}
```

所以 `finish_add_group(...)` 的作用是：

- 把“新 group 已写入文档”推进到“参与重建、刷新 UI、必要时继续交互”


## 5. `GroupExtrude` 里真正存了什么

定义在：

- `src/document/group/group_extrude.hpp`

```cpp
class GroupExtrude : public GroupSweep {
public:
    enum class Direction { NORMAL, ARBITRARY };
    Direction m_direction = Direction::NORMAL;

    glm::dvec3 m_dvec = {0, 0, 1};

    enum class Mode { SINGLE, OFFSET, OFFSET_SYMMETRIC };
    Mode m_mode = Mode::SINGLE;
    double m_offset_mul = -1;

    void generate(Document &doc) override;
    void update_solid_model(const Document &doc) override;
};
```

`Extrude` 本身不是实体，而是“拉伸特征定义”。  
它主要保存：

- `m_source_group`
  - 输入草图来自哪个 group
- `m_wrkpl`
  - 采用哪个工作平面
- `m_dvec`
  - 拉伸向量
- `m_mode / m_offset_mul`
  - 拉伸模式


## 6. `generate(...)` 和 `update_solid_model(...)` 是两回事

### 6.1 `generate(...)`：生成派生显示/编辑几何

代码在：

- `src/document/group/group_extrude.cpp`

```cpp
void GroupExtrude::generate(Document &doc)
{
    generate(doc, Side::TOP);
    if (has_side(Side::BOTTOM))
        generate(doc, Side::BOTTOM);
}
```

它会从 `m_source_group` 里拿输入实体：

```cpp
for (const auto &[uu, it] : doc.m_entities) {
    if (it->m_group != m_source_group)
        continue;
    if (it->m_construction)
        continue;
    ...
}
```

然后把 2D 草图变成 3D 派生几何，比如：

```cpp
auto &new_line = doc.get_or_add_entity<EntityLine3D>(new_line_uu);
new_line.m_p1 = wrkpl.transform(li.m_p1) + dvec;
new_line.m_p2 = wrkpl.transform(li.m_p2) + dvec;
new_line.m_group = m_uuid;
new_line.m_kind = ItemKind::GENRERATED;
```

所以 `generate(...)` 主要更新的是：

- leader line
- 顶面复制出来的 3D 线/弧/圆
- extrusion 侧边线

也就是给视图和编辑交互用的派生实体。


### 6.2 `update_solid_model(...)`：生成实体模型

代码很短：

```cpp
void GroupExtrude::update_solid_model(const Document &doc)
{
    m_solid_model = SolidModel::create(doc, *this);
}
```

真正 OCC 拉伸发生在：

- `src/document/solid_model/solid_model_extrude.cpp`

```cpp
auto face_builder = FaceBuilder::from_document(doc, group.m_wrkpl, group.m_source_group, offset);
mod->m_shape = BRepPrimAPI_MakePrism(face_builder.get_faces(), gp_Vec(dvec.x, dvec.y, dvec.z));
```

也就是说：

- 先从 source group + workplane 里整理出 face
- 再用 OCC 的 `BRepPrimAPI_MakePrism` 拉伸
- 生成这个特征的实体模型


## 7. `rebuild(...)` 后，Document 是怎么更新的

`finish_add_group(...)` 里调用：

```cpp
m_core.rebuild("add group");
```

而 `Core::rebuild(...)` 最核心的一句是：

```cpp
get_current_document().update_pending();
```

位置：

- `src/core/core.cpp`

所以真正的文档更新总调度器是：

- `Document::update_pending(...)`


## 8. `Document::update_pending()` 的三阶段

核心代码在：

- `src/document/document.cpp`

```cpp
if (index >= first_generate_index) {
    generate_group(*group);
}
if (index >= first_solve_index) {
    solve_group(*group, dragged);
}
if (index >= first_update_solid_model_index) {
    update_solid_model(*group);
}
```

它按 group 顺序，从 pending 起点往后跑三段流水线：

### 8.1 `generate_group(...)`

```cpp
gg->generate(*this);
```

作用：

- 重新生成 group 的派生实体
- 比如 extrude 的 leader line、顶面线、侧边线

### 8.2 `solve_group(...)`

```cpp
System system{*this, group.m_uuid};
const auto res = system.solve();
system.update_document();
```

作用：

- 跑约束求解器
- 更新 group 的 DOF、求解状态、实体参数

### 8.3 `update_solid_model(...)`

```cpp
if (auto gr = dynamic_cast<IGroupSolidModel *>(&group))
    gr->update_solid_model(*this);
```

作用：

- 对有实体模型能力的 group 更新 solid model
- 比如 extrude、revolve、fillet 等

所以 `update_pending()` 的核心就是：

```text
generate -> solve -> update_solid_model
```


## 9. 为什么只从某个 group 往后更新

因为特征建模是链式依赖的。

比如：

```text
Sketch 1
  -> Extrude 1
  -> Fillet 1
```

如果你改的是 `Extrude 1`，那通常不需要回头重算 `Sketch 1`，  
但 `Extrude 1` 后面的 `Fillet 1` 需要跟着更新。

所以这个系统不是每次全量重建，而是：

- 记住“从哪个 group 开始脏了”
- 然后只从那里往后跑 `generate / solve / update_solid_model`


## 10. rebuild 完成后，谁通知 UI

在：

- `src/core/core.cpp`

```cpp
void Core::rebuild_finish(bool from_undo, const std::string &comment)
{
    if (!from_undo) {
        m_documents.at(m_current_document).history_push(comment);
    }
    m_signal_rebuilt.emit();
}
```

这说明：

- rebuild 完成后
- Core 会发出 `signal_rebuilt()`

这个信号就是 UI 刷新的业务通知。


## 11. Editor 为什么不是“只能接收 GTK 事件”

这里要分清两种方向：

- GTK 控件把用户事件发给 `Editor`
- `Core` 把“数据已更新”的业务信号发给 `Editor`
- `Editor` 再主动调用控件 API 去更新界面

所以 `Editor` 是中控层，不是单纯的事件接收器。

### 11.1 GTK -> Editor

比如左侧树：

```cpp
m_workspace_browser->signal_add_group().connect(sigc::mem_fun(*this, &Editor::on_add_group));
```

意思：

- GTK 控件产生事件
- `Editor` 来处理

### 11.2 Core -> Editor

比如 rebuild 完之后：

```cpp
m_core.signal_rebuilt().connect([this] {
    ...
    m_workspace_browser->update_documents(...);
});
```

以及：

```cpp
m_core.signal_rebuilt().connect([this] {
    if (m_group_editor) {
        if (m_core.get_current_group() != m_group_editor->get_group())
            update_group_editor();
        else
            m_group_editor->reload();
    }
});
```

意思：

- Core 发 rebuilt 信号
- Editor 收到后刷新左侧树、右侧属性区等 UI

### 11.3 Editor -> GTK 控件方法调用

比如画布刷新：

```cpp
get_canvas().request_push();
```

以及：

```cpp
m_workspace_browser->update_documents(...);
m_workspace_browser->select_group(...);
get_canvas().set_selection(...);
```

这些都不是“Editor 反向发 signal”，而是：

- `Editor` 主动调用控件对象的方法

所以它的真实结构是：

```text
用户事件: GTK控件 -> Editor
业务更新: Core -> Editor
界面刷新: Editor -> GTK控件方法
真正绘制: GTK -> Canvas::on_render()
```


## 12. 画布为什么能被 Editor 推动重绘

不是因为 `Editor` 直接画 OpenGL，而是因为它调用了 `Canvas` 的请求重绘接口。

先看：

```cpp
get_canvas().request_push();
```

而 `Canvas::request_push()` 内部是：

```cpp
void Canvas::request_push()
{
    m_push_flags = PF_ALL;
    queue_draw();
}
```

`queue_draw()` 是 GTK 的标准“请求重绘”接口。

所以链路是：

```text
Editor 调 Canvas::request_push()
  -> Canvas 调 queue_draw()
  -> GTK 安排这个 GLArea 重绘
  -> GTK 回调 Canvas::on_render()
```

因此：

- `Editor` 可以主动推动控件重绘
- 但真正的绘制回调，仍然是 GTK 调 `Canvas::on_render()`


## 13. `CanvasUpdater` 在这里的作用

很多编辑路径里会先创建一个：

```cpp
CanvasUpdater canvas_updater{*this};
```

它的析构函数会在作用域结束时统一触发一次画布刷新：

```cpp
Editor::CanvasUpdater::~CanvasUpdater()
{
    ...
    if (m_editor.m_canvas_update_pending == 0)
        m_editor.canvas_update_keep_selection();
}
```

所以它是一个小的 RAII 刷新器，作用是：

- 把一段编辑操作结束后的画布刷新统一收口


## 14. 最后用 `Extrude` 串一遍完整流程

```text
用户点击新增 Extrude
  -> Editor::on_add_group(EXTRUDE)
  -> doc.insert_group<GroupExtrude>(...)
  -> 填 m_wrkpl / m_dvec / m_source_group

  -> finish_add_group(...)
  -> doc.set_group_generate_pending(new_group->m_uuid)
  -> m_core.rebuild("add group")

  -> Document::update_pending()
       -> generate_group(extrude)
            -> 生成 leader line / 顶面线 / 侧边线
       -> solve_group(extrude)
            -> 更新约束与参数状态
       -> update_solid_model(extrude)
            -> FaceBuilder::from_document(...)
            -> BRepPrimAPI_MakePrism(...)

  -> Core::rebuild_finish()
  -> m_signal_rebuilt.emit()

  -> Editor 收到 rebuilt
       -> 刷 workspace browser / group editor / constraints 等 UI
       -> 通过 CanvasUpdater / canvas_update() 刷新画布

  -> Editor::render_document()
  -> Renderer::render()
  -> get_canvas().request_push()
  -> GTK 调 Canvas::on_render()
  -> 屏幕显示最新结果
```


## 15. 要害总结

- `on_add_group(...)` 负责把新特征节点和基础参数写进 `Document`
- `WITH_BODY` 的作用不是生成 shape，而是让该 group 成为新的 body 起点
- `finish_add_group(...)` 负责命名、标记 pending、触发 rebuild、刷新左侧树、必要时接续 tool
- `GroupExtrude::generate(...)` 生成派生显示/编辑几何；`update_solid_model(...)` 才生成实体模型
- `Document::update_pending()` 是整个文档更新总调度器，按顺序执行 `generate -> solve -> update_solid_model`
- rebuild 完后，`Core` 通过 `signal_rebuilt()` 通知 `Editor`
- `Editor` 不是只能接收 GTK 事件，它同时接收 Core 的业务信号，并主动调用 GTK 控件方法刷新界面
- 画布刷新不是 `Editor` 直接画，而是 `Editor -> Canvas::request_push() -> GTK queue_draw -> Canvas::on_render()`
